# D8 evidence base: what the brainstorm already knows

Written 2026-09-16, while the hop-3 measurement waited on an XPI install.
This is not a proposal. It is the evidence D8's brainstorm should not have
to re-derive, plus the questions that are genuinely still open. The roadmap
entry for D8 stays the statement of the problem; this file is its dossier.

## What D8 has to decide

From the user, 2026-09-13, watching a hop-3 fill crawl: "We need more ways
to minimize the number of fetchs." Three claims sit inside that, and only
the third is settled:

1. **The rate is bad.** B50 measured and changed it.
2. **The plugin slows down.** Narrowed the same day by walking the item-tree
   check: Zotero's own panes stay responsive, "only the plot lags". So the
   cost is the graph's own rebuild and redraw per landing, not leakage into
   Zotero. D10 and D13 are that cost's neighbours.
3. **Depth 6 is unreachable.** A rail that offers six hops is capped in
   practice at three by wall clock. This is the one that bites, because
   Stage 4 is built on the fill.

And a structural point from the same walk, which changes what "depth" even
means: in the citers direction each hop is roughly a step forward in time,
so "Hop 5 is already 2026, so in this case there are no new items yet."
Rows past that are structurally empty, not merely unfetched — and today a
row reading `not fetched` and a row that can never hold anything look
identical.

## What is measured, and what is not

**Measured (2026-09-14, in the test Zotero, by wrapping `Zotero.HTTP.request`):**

- Every failed expansion landed at 15.0–15.2 s, which is
  `RELATIONSHIP_PROVIDER_TIMEOUT_MS` — not the network and not the rebuild.
- Semantic Scholar answered HTTP 429 in about 0.46 s per request, 23 of 25
  through hop 1 in one run. Neither profile has a Semantic Scholar key.
- A shell polling the same path at the plugin's pace got 200 while Zotero
  got 429 in the same seconds, then itself got 429 after about 190
  requests. So a shell probe is not evidence about Zotero's rate.

**Changed since, and therefore unmeasured:**

- B50: no retry on a 429, switch provider at once, a refusing provider sits
  out 30 s / 1 min / 2 min / then 5 min, cool down only when nobody is left
  to ask, and a refused snapshot is never stored.
- B63 (2026-09-16): the OpenCitations lookup works again, so the cycling
  that kept `n left` from falling should stop, and every relation page now
  costs one round trip instead of two.

**Not measured at all:** the user's own profile, where the counts did climb.
That is the pending walk, and it is what D8 should be held on.

## The cost model, as the code stands today

Per expansion, for one paper, in one direction:

- one lookup per provider tried (`lookupProviderRecord`), unless a hint
  supplies the provider's work ID;
- then relation pages from the one provider that answers, at that
  provider's page size.

Citers paging providers, in plan order: **Semantic Scholar → OpenCitations
→ OpenAlex** (OpenAlex only with a key, which the user's profile has).

| Provider         | Spacing | Page size | Note                                             |
| ---------------- | ------- | --------- | ------------------------------------------------ |
| Semantic Scholar | 1100 ms | 200       | keyless here; a key buys quota, never speed      |
| OpenCitations    | 400 ms  | 1000      | Meta is 180 req/min per IP                       |
| OpenAlex         | —       | —         | keyless returns an empty page before any request |

So the fill's floor is set by Semantic Scholar's 1.1 s spacing when it is
answering, and by the cool-down ladder when it is not.

## What D8 must not decide alone

Each of these is filed separately and each would be repainted by whatever
D8 settles. The brainstorm should at least say which of them it moots.

- **D7** — the rail's three numbers are in two units and read as competing
  predictions. The user proposed a progress bar; the spec dropped exactly
  that, and the parent count is the only figure that converges.
- **B51** — opening a deeper hop strands the shallower one's remaining work.
  The user calls the skip itself a feature, so the fix is not to forbid it.
- **B54** — verify a reopen does not refetch what the store already holds.
  The spec says the expensive half is safe; nobody has checked against
  B50's rate. Known leak: failed papers come back after a reopen.
- **B55** — a graph saved while stopped reopens fetching. One line of state,
  but the real question is whether a reopen should ever fetch unasked.
- **B47** — nodes move far more than new data should move them, at the
  most-cited edge the user reads the plot from.
- **D11** — a reference fill lands many papers with no readable metadata.
  First hypothesis: hydration starved behind membership requests, i.e. a
  symptom of the rate. Second: `10.5555` DOIs that were never resolvable.
- **D10, D13** — hop depth encoded as opacity, and edges that stop carrying
  information at a filled graph's density. Both are the per-landing redraw
  cost from the reader's side.
- **B64** — a manual Refresh waits out the 15 s timeout while Semantic
  Scholar refuses. The roadmap already says this belongs with D8.
- **B67** — the fill is inferred from `retryRefusals === false`. If D8 adds
  fill-only paths, that inference should become explicit first.

## Options the roadmap already names

Listed so the brainstorm starts from them rather than rediscovering them,
with what the evidence now says:

1. **Expand only what the reader has looked at or asked for.** The plan
   already carries `selectedKey`, `hoveredKey` and `onScreenKeys`, so the
   shape exists.
2. **Expand the most-cited parents first, then stop.** Needs a count before
   expanding — which is exactly what OpenCitations can no longer supply and
   Semantic Scholar refuses to.
3. **A budget the reader sets.** Interacts with D7: a budget is a number
   that converges, which is what the rail lacks.
4. **Reuse what the store already holds before any request.** B54 says this
   may already be true and unverified.
5. **Derive the offered depth from the data** rather than fixing it at 6,
   which also answers the structurally-empty row above.

## Questions the brainstorm still has to answer

- What does the reader actually want a hop _for_? Every option above
  optimises a different answer.
- Should a fill ever run unasked (B55), and if so, how far?
- Is breadth-first over every parent the right shape at all, or is the
  fill really a search the reader steers?
- What happens to a partly-filled hop when a deeper one opens (B51)?
- Should hops past 3 be offered before this is answered?
